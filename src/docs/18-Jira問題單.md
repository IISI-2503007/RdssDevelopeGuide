# 18. Jira 問題單建單與狀態流程

驗測期間（PMO 驗測、資服司驗測、內部自測）發現的問題，一律在 Jira KAN 專案開「子任務」。這一章規定單子怎麼建、狀態怎麼押、每個人身上只會有哪些狀態。每日修復進度統計與「疑似漏押」清單都照這份規則跑，押錯的單會被列出來。

2026-11-09 定版。

---

## 📌 兩種來源，用標籤分

| 標籤 | 誰提的 | 修完誰複測 |
|---|---|---|
| `PMO驗測` | PMO 提出的 | 交回 PM（Feeble Liu），PM 丟回 PMO 自己測 |
| `自行驗測` | 不是 PMO 提的，我們自己發現的（資服司驗測現場、內部自測、開發時發現） | 該模組測試負責人複測 |

- 建單時一定選一個，沒選就看不出修完該轉給誰。
- **種類只看標籤，不看建立人**：PMO 的單是小助理用 Feeble Liu 帳號建的，但 PM 偶爾也會自己建資服司的單。

## 🔁 狀態流程

| 步驟 | 誰 | 情況 | 押狀態 | 受託人轉給 |
|---|---|---|---|---|
| 建單 | 建單人 | 確認是問題 | 待處理 | 該模組 PG |
| 建單 | 建單人 | 一看就是新需求或暫時不修 | 待確認 | Feeble Liu |
| 處理 | PG | 修完，`自行驗測` 的單 | 已修正 | 該模組測試負責人 |
| 處理 | PG | 修完，`PMO驗測` 的單 | 已修正 | Feeble Liu |
| 處理 | PG | 修不了或判定是新需求 | 待確認 | Feeble Liu |
| 複測 | 測試負責人 | 複測通過 | 完成 | Feeble Liu |
| 複測 | 測試負責人 | 複測沒過 | 退回修改 | 該模組 PG，留言寫哪裡沒過 |

- 「處理中」在統計上 = Jira 的 進行中 ＋ 退回修改。
- 不會有「PG 修完丟給測試人員、測試人員再押待確認」：新需求／修不了在 PG 那一步就押待確認轉 Feeble。
- 複測結果寫留言，不要改描述。

## 👤 每個角色身上只會有這些狀態

| 角色 | 身上該有的狀態 | 出現就是漏押／漏轉 |
|---|---|---|
| PG（模組開發負責人） | 待處理、處理中（進行中／退回修改） | 已修正（修完沒轉人）、待確認、完成 |
| 測試負責人 | 已修正（限 `自行驗測`，等複測） | 待處理（PG 修完沒押已修正）、待確認、完成（複測完沒轉回 Feeble） |
| Feeble Liu（PM） | 待確認、完成、已修正（限 `PMO驗測`） | 待處理、處理中（該押待確認沒押） |
| 未指派 | 無 | 全部（建單沒押受託人就是漏押） |

員額申請（alvis.wu）、甄選作業（Owen Su）的 PG 與測試負責人是同一人，已修正掛自己是正常的。

## 📝 建單必填

| 欄位 | 必填 | 規定 |
|---|---|---|
| 議題類型 | 必填 | 子任務 |
| 父系 | 必填 | 掛到該功能的「功能」議題；找不到問該模組 PG，不要隨便掛 |
| 摘要 | 必填 | 照下方標題格式 |
| 描述 | 必填 | 照下方描述模板 |
| 標籤 | 必填 | `PMO驗測` 或 `自行驗測` 擇一 |
| 優先順序 | 必填 | 建單人自判：Highest 立刻修、已影響測試或功能運作；High 影響主流程；Medium 一般；Low 不影響主流程的邊角 |
| 受託人 | 必填 | 待處理 → 該模組 PG；待確認 → Feeble Liu。不可空白 |
| 狀態 | 必填 | 確認是問題 → 待處理；新需求或暫不修 → 待確認 |
| 截圖／檔案（雲端連結） | 選填 | **資安規定：Jira 不放附件**，不用 Jira 的附件功能、不直接附檔。截圖與測試用的檔案一律上傳雲端（SharePoint），連結貼在描述的「截圖」行。**雲端圖片檔名一律改成單號**，如 `KAN-1849.png`；同一張單多張圖不用自己編號，讓系統取成 `KAN-1849 (1)`、`KAN-1849 (2)`。單號建單後才有，所以先建單、再上傳改名、再把連結貼回描述 |

## 🏷️ 標題格式

```
(新需求)[來源YYYYMMDD][模組] 頁面或功能 > 問題一句話
```

| 段 | 規定 |
|---|---|
| (新需求) | 不管是測試人員還是 PG 發現的，只要判定是新需求，最前面一定加「(新需求)」四個字（半形括號）。同時狀態押待確認、受託人 Feeble Liu。不是新需求就沒有這段 |
| [來源YYYYMMDD] | PMO 的單寫 `[PMO驗測20261106/渝傑]`，斜線後是 PMO 測試人員姓名；資服司驗測現場測出來的寫 `[資服司驗測20261106]`；不是在資服司驗測場合發現的（內部自測、開發時發現）寫 `[自行驗測20261106]`。日期是發現當天 |
| [模組] | 九個模組名之一 |
| 頁面或功能 | 選單路徑最後一層或畫面名，有頁面代號（如 PNR023b01）可放這裡 |
| 問題一句話 | 60 字內講完「哪裡怎麼了」。帳號、測資、步驟、截圖都寫到描述，不塞標題 |

例：

```
[資服司驗測20261106][役男管理] 出境狀態查詢 > 已核准役男未顯示三顆函文按鈕
(新需求)[資服司驗測20261029][役男管理] 健保申報匯出 > 退保月份要預設系統年月
[PMO驗測20260910/渝傑][甄選作業] 錄用名冊核定查詢 > 選次別查詢後下方按鍵未依舊系統顯示
```

舊的「【PMO/姓名】」「(待確認)」「(re-test)」前綴不再用；已建的單不用回頭改。待確認看狀態、複測看留言。

## 🧾 描述模板

測試人員在驗測現場能記下四件事就夠了。不寫環境（修復與驗證都在板橋 SIT 再包版，環境沒有資訊量），不要求逐步操作步驟（麵包屑加測試資料就能重現）。

```
麵包屑:
測試資料:
現有問題:
預期結果:
截圖:
```

| 行 | 寫什麼 |
|---|---|
| 麵包屑 | 問題發生的地方，選單 > 頁面 > 按鈕 |
| 測試資料 | 登入帳號、用的檔案（放雲端，連結寫在截圖行）、身分證字號、年度、案號等，PG 要能照著重現 |
| 現有問題 | 問題是什麼、畫面怎麼呈現，錯誤訊息原文照貼 |
| 預期結果 | 要解決什麼、解決後正確呈現為何；舊系統怎麼做就寫「比照舊系統：…」 |
| 截圖 | 選填，沒有寫「無」；貼雲端連結，不掛 Jira 附件；檔名規則見上表 |

- 前四行都要有字，沒有就寫「無」，不能只貼一個截圖連結或一張 PMO 表格就送出。
- PMO 的單可以把 PMO 原始測試紀錄表格貼在模板下面，但前四行還是要填。

新需求的單把「現有問題／預期結果」換成：

```
需求內容:要加什麼、改什麼
提出來源:誰提的（資服司承辦／PMO／內部），哪次會議或哪封信
```

### 範例

```
摘要:[資服司驗測20261030][員額申請] 審查作業指引 > 查驗C 審查結果確認 > 點「下載審查總分」出現異常訊息
標籤:自行驗測   優先順序:High   受託人:alvis.wu   狀態:待處理

麵包屑:員額作業 > 員額審查作業 > 審查作業指引 > 查驗C 營運計畫審查 > 審查結果確認

預期結果:下載審查總分 Excel
```

## 🔍 會被列進「疑似漏押」的情況

每日統計會附第二張表，逐條套下面規則；該補的人用 Jira 變更紀錄往前推到「最後一個動狀態或受託人卻沒走完流程的人」，PM 只是最後接收方不算，沒人動過就是建單人。**沒選標籤一律算建單人**。

| 目前狀態 | 受託人／標籤 | 疑似問題 |
|---|---|---|
| 任何 | 未指派 | 建單沒押受託人 |
| 待處理／處理中 | Feeble Liu | 新需求／暫不修該押待確認沒押 |
| 待處理／處理中 | 本模組測試負責人 | PG 修完沒押已修正 |
| 待處理／處理中 | 不是本模組 PG | 受託人派錯人 |
| 待處理／處理中 | 本模組 PG 但沒標籤 | 沒選標籤 |
| 已修正 | 沒標籤 | 看不出該轉測試負責人還是 Feeble |
| 已修正 | `PMO驗測` 但不是 Feeble | PMO 單已修正該轉回 Feeble |
| 已修正 | `自行驗測` 但不是本模組測試負責人 | 修完忘了轉測試負責人 |
| 待確認 | 不是 Feeble | 待確認該掛 Feeble |
| 完成 | 不是 Feeble | 複測完沒轉回 Feeble |
| 任何 | 標題有「(新需求)」但狀態不是待確認 | 新需求沒押待確認 |

統計數字照 Jira 現況，不替人改；押錯回 Jira 改，下次跑自然對。

## ✅ 建完自我檢查

1. 標籤有押而且押對：PMO 提的押 `PMO驗測`，其他一律 `自行驗測`，只能選一個。
2. 狀態押對：一般問題「待處理」；新需求或暫不修「待確認」，而且標題最前面有「(新需求)」。
3. 受託人跟狀態對得上：待處理 → 該模組 PG；待確認 → Feeble Liu。不能空白。
4. 描述的麵包屑、測試資料、現有問題、預期結果四行，每一行冒號後面都有字，沒有的寫「無」。
5. 截圖和檔案都是雲端連結貼在描述，Jira 本身沒有掛附件；雲端檔名是這張單的單號（如 KAN-1849、KAN-1849 (1)），不是手機或 PMO 給的原始檔名。
