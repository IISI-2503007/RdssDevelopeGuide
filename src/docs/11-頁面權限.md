## 1. 整體架構

```text
HTTP 請求
    │
    ▼
[1] JwtTokenFilter              → 驗證 JWT Token，解析使用者身份，注入 SecurityContext
    │
    ▼
[2] Spring Security             → 確認使用者是否已登入（hasAnyAuthority 規則）
    │
    ▼
[3] WebUriAuthorizationFilter   → 比對請求 URI 與使用者角色擁有的 FUNC_CODE，決定是否放行
    │
    ▼
[4] Controller / Service        → 業務邏輯內部可再依角色細分行為（如 isRdssOffice()）
```

## 2. 核心資料表

### RDSYS_PERMISSION（功能頁面主檔）

Entity：`moi.rdss.platform.entity.RdsysPermission`

| 欄位 | 型別 | 說明 |
|---|---|---|
| `SN` | DECIMAL(10) | 主鍵，流水號 |
| `FUNC_CODE` | VARCHAR(15) | 功能代碼（如 QSP042B02）— 核心欄位 |
| `ACTION_PATH` | NVARCHAR(60) | 功能路徑，對應前端頁面路由。依系統慣例填入 FUNC_CODE 的值，確保選單連結路徑一致 |
| `NAME_TEXT` | NVARCHAR(80) | 選單顯示名稱 |
| `PARENT_SN` | DECIMAL(10) | 上層選單的 SN（NULL 表示根節點） |
| `ITEM_ORDER` | DECIMAL(6) | 選單排序 |
| `VISIBILITY` | DECIMAL(1) | 全域顯示開關：1 = 開放，0 = 全域關閉 |
| `LINK_DISABLE` | DECIMAL(1) | 連結是否停用 |
| `CERT_USAGE` | DECIMAL(2) | 是否啟用憑證：0=否，1=是，-1=強制 |

### RDSYS_PERMISSION_USER（角色與功能對應表）

Entity：`moi.rdss.platform.entity.RdsysPermissionUser`

> ⚠️ 重要：
> - `ACCOUNT` 欄位儲存字串 `'NULL'`（4個字元），不是 SQL NULL，代表「適用整個 USER_TYPE」
> - `S_TIME_ZONE` / `E_TIME_ZONE` 為 NOT NULL 欄位，無時區限制時必須填字串 `'NULL'`

| 欄位 | 說明 |
|---|---|
| `PERMISSION_SN` | 對應 RDSYS_PERMISSION.SN |
| `USER_TYPE` | 角色代碼，對應 Role enum 的 accType |
| `ACCOUNT` | 字串 `'NULL'` = 角色預設權限；填實際帳號 = 個人特殊權限 |
| `START_TIME` / `STOP_TIME` | 權限起迄時間（可為 SQL NULL） |
| `S_TIME_ZONE` / `E_TIME_ZONE` | NOT NULL 欄位，無時區限制時填字串 `'NULL'` |

## 4. URI 比對規則（normalization）

`WebUriAuthorizationFilter` 將請求 URI 正規化後，與 FUNC_CODE 前 6 碼做 `startsWith` 比對。

> ⚠️ 關鍵：只取 FUNC_CODE 前 6 碼，代表同模組下所有子頁面共用模組前綴授權。

```java
// 例：/adm_011b04/showPermissions
// 1. 去除開頭 '/'   → adm_011b04/showPermissions
// 2. 轉大寫         → ADM_011B04/SHOWPERMISSIONS
// 3. 去除第 4 位 '_' → ADM011B04/SHOWPERMISSIONS
// 比對 FUNC_CODE 前 6 碼：ADM011 → startsWith 符合 ✅

private String normalization(String str) {
    StringBuilder sb = new StringBuilder(StringUtils.upperCase(str));
    if (sb.length() > 1 && sb.charAt(0) == '/') sb.deleteCharAt(0);
    if (sb.length() > 3 && sb.charAt(3) == '_') sb.deleteCharAt(3);
    return sb.toString();
}
```

## 5. 快取機制

> ⚠️ `functionCodesCacheStore` 過期時間為 **7 天**，登出登入不會清除。
> 修改 `RDSYS_PERMISSION_USER` 後，必須重啟服務（Jenkins 重新部署）才會生效。

| 快取 | Key | Value | 用途 |
|---|---|---|---|
| `authenticationCacheStore` | account | Authentication | 快取使用者 Authentication |
| `functionCodesCacheStore` | role (accType string) | List\<String\> | 快取每個 Role 對應的 FUNC_CODE 前 6 碼 |

## 6. 新增頁面權限 SOP

### Step 1　確認 FUNC_CODE 命名

格式：`{模組前綴 3碼}{功能群組 3碼}{頁面代碼 3碼}`，例如 `QSP042B03`

| 前綴 | 模組說明 |
|---|---|
| RDP | 一般公開頁面 |
| ADM | 行政管理 |
| PNR | 員額申請／審查 |
| QSP | 甄選作業 |
| REM | 役男管理 |
| MTM | 管訓作業 |
| PTM | 役男薪資 |
| AEP | 績效評核 |
| RFM | 基金管理 |

情境 B — 查詢未使用群組代碼：

```sql
SELECT DISTINCT SUBSTRING(FUNC_CODE, 1, 6) AS GROUP_CODE
FROM RDSYS_PERMISSION
WHERE FUNC_CODE LIKE 'QSP%'
ORDER BY GROUP_CODE;
```

### Step 2　在 RDSYS_PERMISSION 新增頁面資料

> ⚠️ `ACTION_PATH` 依系統慣例填入 FUNC_CODE 的值，確保選單連結指向正確路徑。
> **注意**：`normalization` 比對的對象是實際 HTTP 請求 URI（即 Controller 的 `@RequestMapping` 路徑），不是 `ACTION_PATH` 欄位本身。導致 403 的直接原因是 Controller 路徑未對應 FUNC_CODE，而非 ACTION_PATH 設錯。

```sql
SELECT MAX(SN) FROM RDSYS_PERMISSION;
SELECT * FROM RDSYS_PERMISSION WHERE FUNC_CODE = 'QSP042B03';

INSERT INTO RDSYS_PERMISSION (
    SN, FUNC_CODE, ACTION_PATH, NAME_TEXT, DESCRIPTION,
    PARENT_SN, ITEM_ORDER, VISIBILITY, LINK_DISABLE, LINK_PARAMETER, CERT_USAGE
) VALUES (
    999,
    'QSP042B03',
    'QSP042B03',  -- ★ ACTION_PATH = FUNC_CODE
    '新頁面名稱', '功能說明文字',
    (SELECT SN FROM RDSYS_PERMISSION WHERE FUNC_CODE = 'QSP042B02'),
    10, 1, 0, NULL, 0
);
```

### Step 3　在 RDSYS_PERMISSION_USER 新增角色權限

```sql
SELECT * FROM RDSYS_PERMISSION_USER
WHERE PERMISSION_SN = (SELECT SN FROM RDSYS_PERMISSION WHERE FUNC_CODE = 'QSP042B03')
  AND USER_TYPE = 17;

INSERT INTO RDSYS_PERMISSION_USER (
    PERMISSION_SN, USER_TYPE, ACCOUNT, START_TIME, STOP_TIME, S_TIME_ZONE, E_TIME_ZONE
) VALUES (
    (SELECT SN FROM RDSYS_PERMISSION WHERE FUNC_CODE = 'QSP042B03'),
    17, 'NULL', NULL, NULL, 'NULL', 'NULL'
);
```

### Step 4　建立 Controller

```java
// normalization('/QSP042B03/queryList') → 'QSP042B03/QUERYLIST'
// findFunctionCodesByRole 回傳前 6 碼：'QSP042'
// startsWith 符合 ✅

@RestController
@RequestMapping("/QSP042B03")
public class Qsp042b03Controller {
    @PostMapping("/queryList")
    public ResponseEntity<?> queryList(...) { ... }
}
```

### Step 5　Service 內的角色細分（選用）

```java
AccountDetails accountDetails = (AccountDetails) authentication.getPrincipal();

if (accountDetails.isRdssOffice()) {
    // 專案辦公室：可看全部資料
} else if (accountDetails.isNCAAccount()) {
    // 役政司：只能看自己管轄的資料
}
```

## 7. VISIBILITY vs RDSYS_PERMISSION_USER 使用時機

| 需求 | 應調整的位置 |
|---|---|
| 讓某個角色看不到某頁面 | 刪除 RDSYS_PERMISSION_USER 中該角色的對應資料 |
| 讓某個特定帳號才能看到 | 在 RDSYS_PERMISSION_USER 中加入指定 ACCOUNT |
| 讓所有角色都看不到（暫停功能） | 將 RDSYS_PERMISSION.VISIBILITY 設為 0 |
| 恢復頁面可見 | 將 RDSYS_PERMISSION.VISIBILITY 設為 1，並確認 RDSYS_PERMISSION_USER 有對應資料 |

> 🔴 不要用 `VISIBILITY = 0` 調整單一角色權限，這是全域關閉。

## 8. 前端權限與頁面路由對應機制

### 整體流程

```text
登入
 ↓
後端 /RDP022A01/permission 回傳 permissions 陣列
 ↓
前端將每筆 actionPath 轉換成 href（存入 Local Storage）
 ↓
使用者進入任一頁面
 ↓
前端比對 href === 當前路由路徑
 ↓
相符 → 有權限；不符 → 顯示 403
```

### 前端轉換邏輯（src/store/auth.js）

```js
href: permission.actionPath?.replace('Action.do', '')

hasPermission = path =>
  flattenMenus.some(({ href }) => href === path)
```

### 前端路由產生規則（unplugin-vue-router File-based Routing）

| 前端檔案位置 | 自動產生路由 |
|---|---|
| `src/private/std/studentResumeQuery/index.vue` | `/std/studentResumeQuery` |
| `src/private/work/personQuery/index.vue` | `/work/personQuery` |
| `src/private/test/tst001a01/index.vue` | `/test/tst001a01` |

### 後端 actionPath 填寫規則

格式：`/{模組前綴}/{頁面名稱}Action.do`，replace 後必須與前端路由**完全相符**。

| 後端 actionPath | replace 後 | 對應前端檔案 |
|---|---|---|
| `/std/studentResumeQueryAction.do` | `/std/studentResumeQuery` | `src/private/std/studentResumeQuery/index.vue` |
| `/work/personQueryAction.do` | `/work/personQuery` | `src/private/work/personQuery/index.vue` |
| `/test/tst001a01Action.do` | `/test/tst001a01` | `src/private/test/tst001a01/index.vue` |

### 現有模組前綴對照表

| 模組前綴 | 對應功能 |
|---|---|
| `/admin` | 系統管理 |
| `/aep` | 管考獎懲 |
| `/auth` | 帳號驗證 |
| `/info` | 資訊需求 |
| `/mtm` | 受訓管理 |
| `/pnask` | 員額申請 |
| `/pnexam` | 員額審查 |
| `/qsp` | 甄選作業 |
| `/rem` | 成效管理 |
| `/rfm` | 基金管理 |
| `/std` | 甄選 / 學生 |
| `/work` | 役男管理 |
| `/test` | 測試用（需同步更新 authPaths） |

### actionPath 常見錯誤

```text
// ❌ 後端 actionPath = "TST001A01"
"TST001A01" → replace 後仍為 "TST001A01"（無 / 開頭）→ 永遠比對不到 → 403

// ✅ 後端 actionPath = "/test/tst001a01Action.do"
"/test/tst001a01Action.do" → replace 後為 "/test/tst001a01" → 符合前端路由 → 通過
```

修正後同步事項：
1. 後端將 `actionPath` 改為正確格式
2. 前端建立對應路由檔案
3. 前端 `src/router/index.js` 的 `authPaths` 加入新模組前綴
4. **必須重新登入**以刷新 Local Storage 中的 permissions 快取

## 9. 常見錯誤排查

| 症狀 | 可能原因 | 解法 |
|---|---|---|
| DB 設定正確但仍 403 | Controller `@RequestMapping` 路徑未對應 FUNC_CODE | normalization 比對的是請求 URI，Controller 路徑必須使 `normalization(URI).startsWith(funcCode前6碼)` 成立。ACTION_PATH 依慣例填 FUNC_CODE 值是為了確保選單連結一致，兩者需同步維護 |
| DB 設定正確但仍 403 | 快取尚未清除 | functionCodesCacheStore 過期 7 天，需重啟服務 |
| DB 設定正確但仍 403 | ACCOUNT 填的是 SQL NULL | 應填字串 `'NULL'`（4個字元） |
| DB 設定正確但仍 403 | VISIBILITY = 0 | 全域關閉，將 VISIBILITY 改回 1 |
| Menu Tree 沒有顯示新頁面 | VISIBILITY 或 RDSYS_PERMISSION_USER 未設定 | 確認 VISIBILITY = 1 且有對應角色資料 |
| 前端一直 403 | actionPath 無 `/` 開頭 | 後端改為 `/模組/頁面Action.do` 格式 |
| 前端一直 403 | 新模組未加入 authPaths | 前端 `src/router/index.js` 補上新模組前綴 |
| 後端改了但前端還是舊權限 | permissions 快取於 Local Storage | 必須重新登入 |

## 10. 異動驗證 Checklist

```sql
SELECT * FROM RDSYS_PERMISSION WHERE FUNC_CODE = 'QSP042B03';
SELECT * FROM RDSYS_PERMISSION_USER
WHERE PERMISSION_SN = (SELECT SN FROM RDSYS_PERMISSION WHERE FUNC_CODE = 'QSP042B03');
```

- 以目標角色帳號登入，確認 Menu Tree 是否顯示新頁面
- 直接輸入完整 URL，確認是否可進入（不被 403 擋住）
- 以無授權角色嘗試存取，確認是否回傳 403
- 確認快取是否需要清除（測試環境若未重啟，可能使用舊快取）
- 若有新增 API endpoint，確認 normalization 規則可正確比對
- 前端確認 `actionPath` 格式、`authPaths`、路由檔案三者一致
- 重新登入刷新 permissions 快取後再次驗證
